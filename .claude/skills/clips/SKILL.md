# clips: link in, editable clips out

Paths are relative to the repo root (the folder that holds `streams/` and `.claude/`). `$WORK` is a work folder OUTSIDE the repo (for example the scratchpad). The source video never goes into the repo (it is gitignored: `streams/*/source/`; clip.json keeps its place in `source` and the real file in `source_local`). The small transcript JSON is copied to `streams/<stream>/docs/`.

Layout: everything that runs lives in `.claude/skills/clips/` (scripts by job: `download/`, `transcript/`, `moments/`, `zoom/`, `captions/`; assets; destinations; docs). Content lives in `streams/<YYYY-MM-DD>_<slug>/` (`stream.json`, `clips/<clip-id>/`, `docs/`). `LATEST.md` at the repo root lists the newest clips first. Never write content anywhere else.

## Who does what
This skill is meant to be run by a Sonnet session. Haiku sub-agents (Agent tool, model haiku) do the fixed-command steps. An Opus agent is asked only for hard judgement calls.

| Step | Model | Why |
|---|---|---|
| 0 preflight.py, lessons (`--retros 3`), plan, questions to the user | Sonnet | judgement |
| 2 download, wait, fetch (Kaggle) | Haiku | fixed commands, waiting |
| 3 transcript (captions to json; or start the Whisper job and fetch it) | Haiku | fixed commands |
| 4 run find_moments.py | Haiku | fixed command |
| 3b visual_scan.py (frames, sheets), visual_review_apply.py, merge_moments.py | Haiku | fixed commands, run in parallel with step 4 |
| 3b read the contact sheets with vision (`docs/visual-review-prompt.md`) | Haiku (default); Sonnet when the user asks or Haiku's JSON fails the apply check twice | cheap image reading; the lead keeps the final call |
| 4 read candidates and transcript, set boundaries, write titles and hooks, reject weak ones | Sonnet (Opus advice when two cuts are both plausible or the transcript is unclear) | the core judgement |
| 5 make_clips.py, contact sheets | Haiku | fixed command |
| 5 look at the sheets, decide fixes | Sonnet | judgement |
| 6 plan_zooms frames to zoom targets | Sonnet | needs to see the frame |
| 7 edit_clip.py for a change the user asked for | Haiku runs it; Sonnet maps the user's words to keys | CONTROLS.md is the map |
| 8 checkpoint (automatic), finalise to main, delete VM copies, add lessons | Haiku | fixed commands |
| 9 retro.py, findings and dispositions, incidents | Sonnet (the lead only, under 10 minutes) | judgement: each finding gets exactly one disposition |
| during any job: `jobs.py tick` first, the `send_later` backstop | the lead (Sonnet) | a session that only waits loses the job (2026-11-16) |

Rules: use one Haiku agent per batch of simple steps, not one per command. Give each Haiku agent the exact commands and the expected output. Agents never decide moments.

## 0. Preflight, learn, then plan
Two commands, before anything else (the first run on a machine also reads QUICKSTART.md):
```
python3 .claude/skills/clips/scripts/preflight.py [--stream $ST] [--facecam NAME]      # about 6 s: PASS / WARN / FAIL per check, one-line FIX for each FAIL
python3 .claude/skills/lessons/scripts/query.py --stage plan,download,moments,render,layout,captions,zoom,facecam,publish,infra --retros 3
```
`preflight.py` runs every check that enforces a known incident (`lessons/incidents.json`, each row's `enforced_by`) plus the machine checks of the table above: Kaggle, ffmpeg, numpy/PIL, Node (WARN only), disk free (5 GB), `git ls-remote` works and no `.autosave-pause` is left behind, `jobs.py tick`, the commands the settings do not allow (WARN: tell the user now so they approve before the wait; you never edit settings), every script path and flag cited in SKILL.md and QUICKSTART.md exists, the stream folder is writable, the facecam you will pass exists, and `AUDIT DUE`. A FAIL: say the FIX line to the user, STOP, run it again after the fix. A job that `tick` reports as lost is resumed first (below). `query.py --retros 3` adds the OPEN findings of the last three retros and the open incidents to the lessons; apply every active lesson and do not repeat an open finding. If `preflight.py` prints `AUDIT DUE`, ask the user whether to run the audit (`docs/audit-prompt.md`, one read-only Fable agent, 5 proposals at most); never start it unasked.
Then tell the user the plan in 6 lines: moments, length, layout, captions, zoom targets, facecam.
Animations: for each clip propose 0 to 3 small animations with a time, a preset and a text (`callout-ring` on a key point in the game, `lower-third-tag` for a short label, `impact-burst` at a scream or a hit). Read the transcript and look at frames to pick the times. Ask the user which ones to add. Add only the ones the user agrees to (step 7a). Animations are not the default: new clips get the static editorial title and no progress line (`defaults.json`: `hook.animation none`, `animations.on false`, `progress_bar false`). The animated title, ring, tag, burst and progress line are for highlight videos or when the user asks for them (`hook.animation=reveal`, `animations.on=true`, `animations.progress_bar=true`).

## 1. Ask once
Ask one question set only for what lessons and `.claude/skills/clips/defaults.json` do not already answer. Do not ask about anything the defaults cover.
Always ask which facecam to use. Show the names in `.claude/skills/clips/assets/facecam/library.json` (the default first) and the choice "none". Pass the answer to step 5 as `--facecam NAME` or `--facecam none`.
Her voice: default is the passive reaction with her audio dropped (`facecam.voice=off`). Offer it once, only for `social`-type outputs: "add her voice quietly" = `facecam.voice=low` (her voice is English only; the clip itself can be in any language; needs a facecam item with `audio_usable: true`: girl_surprise_10s, girl_impressed_20s, girl_hype_10s, girl_disbelief_10s or girl_laugh_10s_patched (the default girl_watching_10s has none, so the edit is refused or warns); set both in one edit `facecam.voice=low facecam.video=girl_surprise_10s` and look for "facecam voice low" in the render output; mixed 15 dB under the stream, once, lip-synced; quiet by default, louder only when the user asks, via `facecam.voice_gap_db` (6-24, lower is louder; the user found a strong voice AI-sounding)); "no voice" = `off`. Timed multi-reaction facecam stays backlog (v1.1).
Always ask where the clips will be posted (several allowed): `social` (with the streamer girl, the default), `youtube-shorts`, `instagram-reels`, `clean` (no facecam, for clipping sites), `whop-content-rewards` (rules are per campaign and behind a login: ask the user to paste the campaign brief; until it is filled in the profile has `verified:false` and renders as clean). Profiles are `.claude/skills/clips/destinations/<name>.json`. Only `facecam` and `fps` of a profile are used by the scripts today (`clip_schema.output_for_destination`); `min_seconds`, `max_seconds`, `audio_lufs`, `captions`, `title` and `credit_line_required` are notes for the human, not checked by any script. "Streamer girl: with, without or both?" = `social` and/or `clean`. Pass the answer to step 5 as `--destinations a,b`. Never guess a site's rules: verify them from its own docs or ask.

Length of the video (routes the whole job): if the user did not say it, ask. Under about 90 min = this normal path (steps 2-5). Over 90 min = Long mode (last section), never step 2. To learn the length from the link without downloading: `python3 .claude/skills/clips/scripts/download/kaggle.py info os-dl-NAME "URL"`, then `wait` and `fetch` as in step 2 into `$WORK/info`; `fetch` prints `video: '...', N min -> ...` (the number is also `duration` in seconds in `$WORK/info/info.json`). The download kernel of step 2 also checks the length first and stops with `LONG VIDEO` when it is over 90 min, with nothing downloaded.

## 2. Download (Kaggle CPU kernel)
```
python3 .claude/skills/clips/scripts/download/kaggle.py download os-dl-NAME "URL"
python3 .claude/skills/clips/scripts/download/kaggle.py wait os-dl-NAME $WORK/wait.log   # a long wait: wrap it with jobs.py run (step 8, Long jobs) so it survives an idle container
python3 .claude/skills/clips/scripts/download/kaggle.py fetch os-dl-NAME $WORK/dl
```
Output: `$WORK/dl/video.mp4`, `$WORK/dl/info.json`, `$WORK/dl/*.vtt` (the Kaggle CLI hands the files over inside a `dl/` folder; `fetch` moves them up, so there is no `$WORK/dl/dl/`). `wait` ends normally also when the kernel failed, so after `fetch` check: if `$WORK/dl/video.mp4` is missing, read what `fetch` printed (`kernel says: ...`) or `$WORK/dl/kaggle-log.txt`:
- `LONG VIDEO` = over 90 min, nothing downloaded: go to Long mode.
- `AGE-RESTRICTED` = STOP, ask the user for a file or another link.
- `Sign in to confirm` (YouTube bot check) or `NO METADATA` = run the three commands again with a new NAME, up to 3 times in all (the bot check is often gone on the next try; long mode does the same), then STOP and tell the user plainly; ask for a file or another link.
- `LIVE` = the stream is still running: ask again after it has ended.
- `LIMIT REACHED: kernel ... still QUEUED` printed by `wait` = the Kaggle queue was busy for 20 min; `wait` already deleted that kernel. Run the three commands again with a new NAME (up to 3 times in all), then tell the user.
Never use cookies or proxies. If a command prints `error: the kaggle CLI is not installed` or `Kaggle credentials are missing`, this is a setup problem, not a limit: show that line to the user (QUICKSTART.md).

## 3. Transcript
1. YouTube captions in the video's own language (word-level `.vtt`). Free and instant:
```
python3 .claude/skills/clips/scripts/transcript/vtt_to_transcript.py $WORK/dl/video.hi-orig.vtt $WORK/transcript_hi.json hi
```
(Use the real `.vtt` name from `ls $WORK/dl`.) English auto-captions are usually good. Hindi ones are fair and write English words in Devanagari.
2. If the video has captions, ALWAYS use them (item 1). Whisper is for a video with no captions only (always for Twitch; Twitch is untested: see "Not built yet" at the end). Whisper on the Kaggle T4 measured worse than YouTube captions for Hindi, as measured on 2026-11-15 (the default large-v3, batched 8, VAD 500, chunk 20 measured 66% exact / 77% fuzzy word match against the captions on the first 30 s of three windows on 2026-11-15, the earlier turbo default 21-25%; still below the captions; details in the section "Whisper T4 settings tuning" of `docs/long-mode-report.md`). So when you fall back to Whisper, tell the user plainly BEFORE you start: "This video has no captions. The Whisper transcript is weak for Hindi, so moment picking and captions will be less reliable. Go on, or give another link?" `long_run.py fetch-windows` enforces this: when Whisper would run it STOPS and prints that sentence, and starts nothing until you repeat the command with `--accept-whisper` after the user said go on. Do not use Whisper because captions merely look imperfect (Hindi captions write English words in Devanagari: that is normal). Only when captions are clearly empty or wrong (under about 60 words per minute while he talks) offer Whisper as a choice.
   A video with no captions, of ANY length (also under 90 min), uses the Long mode commands: `long_run.py prepare`, then `fetch-windows --whisper --lang hi` (it picks the best windows first and transcribes only those; long mode was tested on a 32 min video). Do not use the OpenShorts `run.py` path: it outputs finished clips, not a transcript JSON. The Whisper default is large-v3, batched 8, VAD min silence 500 ms, chunk 20 s. ALWAYS pass `--lang hi` for Hindi (and `--lang en` for English): auto language can translate Hindi into English; `long_run.py fetch-windows` refuses a Whisper run on a Hindi/Hinglish stream without `--lang`.
3. The transcript drives moment ranking, complete-moment boundaries, hook and title, captions and word-triggered zooms. Loudness and the YouTube heatmap do not need it.
4. Per language: `.claude/skills/clips/scripts/moments/reaction_words.json` holds the Hindi/Hinglish words and an English list (laughter, "oh my god", "no way", "let's go", "holy", "bro" and so on). The English list is untested on a real stream: for an English video treat the reaction-word signal as weak, rank by replay heat and loudness too, and read the transcript yourself. The Roman map is for Hindi only.

## 3b. Visual moments (what is SEEN; runs in PARALLEL with step 4; `moments.visual=off` skips it)
The transcript finds what is said and how loud it is; this step looks at the VIDEO as well and the merge consults both. Method after bradautomates/claude-video "Watch" (MIT; plugin NOT installed, no code copied, see `NOTICE.md`): frames picked at scene changes with a 16x16 mean-difference dedup, and a vision agent reads them. Needs the whole source video on the machine (step 2 file; the step-3 transcript is optional for the scan, but the reviewer and the merge use it). Run with `$ST`, `$WORK` as above:
```
python3 .claude/skills/clips/scripts/moments/visual_scan.py $ST --source $WORK/dl/video.mp4 [--cam-box x0,y0,x1,y1] [--candidates 14] [--transcript-candidates $ST/docs/moment-finder/candidates.json]
# then the reviewer (sub-agent, prompt in docs/visual-review-prompt.md, writes $ST/docs/visual/reviewer_raw.json)
python3 .claude/skills/clips/scripts/moments/visual_review_apply.py $ST --reviewer haiku      # validates, writes docs/visual/visual_review.json; fix what it prints, never hand-edit around it
python3 .claude/skills/clips/scripts/moments/merge_moments.py $ST                              # docs/moments_merged.json + a table
```
Order (3b needs the step 4 file `candidates.json`, so step 4 starts first):
1. Start `find_moments.py` (step 4, about 20 s).
2. At the same moment start `visual_scan.py` (one Haiku agent, about 1 min per 30 min of 1080p on 4 CPUs, plus about 30 s for 14 sheets). It reads `candidates.json` only after its decode of about 1 minute and sheets the transcript's picks from it; with the file missing it prints a WARNING and sheets none, and a stale file (older run, other `--min/--max`) gives stale picks: re-run `find_moments.py`. A re-run of `visual_scan.py` deletes the old `visual_review*.json` and `reviewer_raw.json` (new windows), and the merge ignores, with a warning, any review whose window start/end differs from the scan.
3. Spawn the reviewer agent as soon as `visual_review_tasks.json` exists, while Sonnet reads `candidates.md`; run `visual_review_apply.py` and the merge when both are done.
No reviewer agent available (no sub-agent tool): the lead reads the sheets itself with the same prompt and writes `reviewer_raw.json`, or skips 3b and tells the user plainly that this job has no visual check (the merge then keeps the transcript order).
The webcam box (fractions of the frame; the streamer's own camera) comes from `--cam-box` or `stream.json` `webcam_box`; without one the 'reaction' part of the energy is dropped. The sheets are 12 frames each (about 1600x700 px, source time burned into every tile); the task file hides where a window came from (transcript pick, visual peak, zone fill) and is shuffled; the sheet set is the transcript's top picks (so the reviewer can confirm or reject them), the strongest visual peaks and one window per zone while the budget lasts.
What the merge does (numbers: `weights.json` "merge"; every row says which rule applied in `notes`): both agree (transcript >= 0.40 and reviewer >= 6) = top; one strong (transcript >= 0.50 or reviewer >= 8) and the other neutral = kept, with a note; a visual-only window (no transcript candidate in the top list overlaps it) is ADDED when the reviewer gave >= 7 (fitted to a 40-55 s complete story on sentence boundaries, then snapped to scene cuts); a transcript candidate the reviewer rejects with a concrete reason (score <= 3) is DEMOTED to the end, with the reason shown, never dropped; every zone keeps a row. No visual files, `--no-visual` or no valid reviewer answer for a window: that window keeps its transcript score and the old order is exactly unchanged (tested). Unreviewed windows with very low visual energy get the note "look at it before cutting". The lead (Sonnet) still writes `docs/moments.json` from `moments_merged.json` plus the candidates; `merge_moments.py --write-moments` only adds the four fields (transcript_score, visual_score, agree, notes) to entries already in `docs/moments.json`, nothing is added, removed or moved.
Cost, from the first run (14 sheets): about 1,440 tokens per sheet image + about 200-500 transcript tokens per window = about 23,000 tokens of content for 30 min (20,100 image + 2,900 transcript, measured; about 1,640 per sheet), 14 sheets, 1 reviewer call; the sub-agent re-reads earlier sheets on each turn, so the billed input is several times higher. About 33,000 for 1 h with `--candidates 20` (estimate). 5-6 h: the whole file is never on the machine (long mode), so only the windows long mode fetched are sheeted: one sheet per window, about 1,900 tokens each, 19,000 per batch of 10, about 57,000 for 30 windows (a 5 h estimate; no real 5 h source tested). Haiku reads the same sheets for less money than Sonnet; its quality here is untested.
On demand: "review visually" (or "check these moments visually") runs this step for the stream (`--candidates N` sets how many sheets; the scan chooses the windows, no flag takes named ones); "no visual review" / `moments.visual=off` skips it and nothing else changes: to make it stick, set `"moments": {"visual": "off"}` in `defaults.json` (`visual_scan.py` then does nothing and `merge_moments.py` ignores the visual files; set it back to `"on"` to run the step). It is a pipeline switch, not a `clip.json` key (CONTROLS.md, section Moments).
Long mode (video over 90 minutes): `visual_scan.py $ST --windows-dir $ST/source/windows` scans only the fetched window files (one sheet per window, its moment range from `docs/moments.json`), then reviewer, apply and `merge_moments.py $ST --candidates $ST/docs/candidates.json` as above. Visual peaks OUTSIDE the fetched windows cannot be found in long mode; the sheets there are a second opinion on the picks, not a search of the 5 h. Built and run only on cut-out windows of the 32 min test video, never on a real long-mode fetch.
Optional Gemini reviewer: only if the user has put their own `GEMINI_API_KEY` in the session environment (check with `[ -n "$GEMINI_API_KEY" ] && echo set`, never print it), a session may use the claude-video plugin's gemini engine (the user installs the plugin) to watch the windows of `visual_review_tasks.json` and write the same JSON answer format to `reviewer_raw.json`; then `visual_review_apply.py --reviewer gemini` and the merge as above. No script of this skill reads, stores, searches for or asks for a key, and no key is read from a dataset or a file. Untested here.
Limits: the cheap energy alone is a weak ranking signal (Spearman 0.12 against the reviewer on the first stream; 1 of the 3 published clips among its top-12 peaks): its main jobs are choosing which windows get a sheet and flagging low-energy picks; the verdict is the reviewer's. Not tested: English stream, Twitch, 5 h, Haiku as reviewer. Report: `docs/visual-moments-report.md`.

## 4. Moments
Create the stream folder first: `python3 .claude/skills/clips/scripts/download/stream_folder.py "Stream title"` prints `streams/<YYYY-MM-DD>_<slug>` (called `$ST` below); write `$ST/stream.json` (title, channel, url, language, duration, date_added, rights, source_available).
```
python3 .claude/skills/clips/scripts/moments/find_moments.py --video $WORK/dl/video.mp4 --transcript $WORK/transcript_hi.json --info $WORK/dl/info.json --clips-dir $ST --out $ST/docs/moment-finder
```
Read `candidates.md` in that folder (when step 3b ran, also `docs/moments_merged.json`: its table and notes say which candidates the video confirms, adds or rejects). Read the transcript of every strong candidate. Fix each start and end so the WHOLE moment is inside: setup, peak, reaction, on sentence boundaries, 40-55 s, the whole story of the moment (setup, peak, aftermath); shorter or longer only when the story needs it. Look at 3 frames of any doubtful one. Write `$ST/docs/moments.json` as `[{"start","end","title","hook","description","score"}]`: it is the only file `make_clips.py` cuts (giving it `moments_merged.json` stops with one error message). The merge table goes to `$ST/docs/moments_merged.json`; `merge_moments.py --write-moments` copies transcript_score, visual_score, agree and notes into the matching entries of `moments.json`, nothing else. Cut ALL good moments. List each rejected candidate in `moments.json` as `{"start","end","status":"rejected","reject_reason":"..."}`: `make_clips.py` and `make_highlights.py` skip it and the reason stays in the file.

## 5. Make the clips
```
python3 .claude/skills/clips/scripts/make_clips.py $WORK/dl/video.mp4 $WORK/transcript_hi.json $ST/docs/moments.json $ST --defaults .claude/skills/clips/defaults.json [--facecam NAME|none] [--destinations social,clean] [--no-snap]
```
Before each clip is built, `make_clips.py` snaps its start and end onto a scene cut (`--snap`, default ON; `--no-snap` turns it off): `scripts/moments/snap_edges.py` runs `ffmpeg scdet` on a 12 s window around each edge of the SOURCE (about 3 s per edge), moves the edge to the nearest cut within 2 s, never into the middle of a spoken word (it uses the transcript word times: a cut inside a word becomes the word's nearest boundary if that is closer to the cut, else the edge stays), never cuts off spoken words by moving inward, and never leaves 40-55 s. It prints before / after for every edge and writes `docs/snap.json`; `docs/moments.json` gets the new times and `snapped_from`. Alone: `python3 .claude/skills/clips/scripts/moments/snap_edges.py SOURCE --start S --end E --transcript T.json` (or `--moments FILE`; for a long-mode window file add `--source-offset N`). Soft dissolves are found at threshold 6 (the default); gameplay with no cuts simply keeps its edges.
Output per clip, in `$ST/clips/<start>-<end>s_<slug>/`: `<output>.mp4` (one per destination, e.g. `social.mp4`, `clean.mp4`), `clip.json` (every setting; `outputs` lists the named files), `poster.jpg`, `post.md` (YouTube title, description, tags, Instagram caption and hashtags, credit, rights, the reused-content and Rockstar warning), `edit-notes.md`, `versions/`. Also `$ST/docs/review.md` (table + layout check), one contact sheet per clip in `$ST/docs/sheets/`, then `streams/index.json` and `LATEST.md` are rebuilt. Show the user `$ST/docs/review.md` and `LATEST.md`. The post kit is a draft: improve the `post` fields in clip.json (use the yt-package and yt-seo skills; YouTube title at most 60 characters, a real description of the moment, no clickbait), then run `python3 .claude/skills/clips/scripts/build_index.py`.

## 6. Pointing zooms (optional, per clip)
```
python3 .claude/skills/clips/scripts/zoom/plan_zooms.py $ST/clips/<id>/clip.json $ST/clips/<id>/social.mp4 $ST/docs/zoom/<id>
```
Look at the gridded frames in `$ST/docs/zoom/<id>/`. Write `zoom_plan.json` there. Add each event in one edit, then render once:
```
python3 .claude/skills/clips/scripts/edit_clip.py $ST/clips/<id>/clip.json 'zoom.plan+={"t":3.0,"x":0.10,"y":0.62,"amp":0.5,"dur":4}' --render
```
`plan_zooms.py` reads the words from the clip's transcript (repo-relative path in clip.json).

## 7. Edit loop
When the user asks for a change, run:
```
python3 .claude/skills/clips/scripts/edit_clip.py CLIP.json key=value [key=value ...] --render
```
No source on this machine (clip.json `source_local` points to a file that does not exist, for example after a fresh clone): download it again (step 2) and copy it to the clip's `source` path (the `source` value in clip.json, normally `streams/<stream>/source/video.mp4`), THEN edit. With `--render` and a missing source the edit is refused BEFORE a version is saved (clip.json and the video never disagree) and the error prints the re-fetch commands (download again, copy to the `source` path); run those, then repeat the edit. Keys and values are in `.claude/skills/clips/CONTROLS.md`. `--render` re-renders EVERY output of the clip (`social.mp4`, `clean.mp4`, ...) next to clip.json and refreshes `streams/index.json`, `LATEST.md` and `post.md`; `--output NAME` renders only one. Send the new clip. Every edit is saved as a numbered version in the clip folder's `versions/` and one line is added to its `edit-notes.md`. Add `--note "why"` to record the reason. `--undo` goes back one version, `--version N` restores version N, `--history` lists the versions.

## Quality: previews in git, masters outside git
Every render goes through a two-pass loudness normalisation (pass 1 measures only the audio of the clip's segment, pass 2 applies `loudnorm` inside the one video pass: `audio.target_lufs` -14, `audio.true_peak` -1.0, `linear=true`, 48 kHz; `audio.target_lufs=null` turns it off) and prints the result (LUFS and true peak of the written file). `output.preset` is `preview` (default: 30 fps, x264 veryfast, CRF 20, AAC 160 kbps, small, this is what goes to git) or `upload` (the source frame rate up to 60 fps, never more than the source has, x264 slow, CRF 17, AAC 192 kbps, `+faststart`, 1080x1920; about 100 MB for 45 s and slow: tell the user the time). `edit_clip.py CLIP.json output.preset=upload --render` writes `<clip dir>/masters/<output name>_upload.mp4` and leaves the preview alone; `streams/**/masters/` is gitignored and a master is NEVER committed (GitHub refuses files over 100 MB). Set `output.preset=preview` again to re-render the git preview. `streams/index.json` does not list masters (they exist only on the machine that rendered them); check `<clip dir>/masters/` on that machine. A source narrower than 1080 px prints a warning (nothing to gain). Where masters live: by default in a private Kaggle dataset per stream, uploaded ONLY when the user asks (then delete the VM copies when they say so). Exact commands (do not run them unasked; `$KAGGLE_USERNAME` and the token are in the environment, `<stream>` is the stream folder name in lower case with hyphens, at most 50 characters):
```
mkdir -p $WORK/masters-ds && cp streams/<stream>/clips/*/masters/*_upload.mp4 $WORK/masters-ds/
echo '{"title": "clips-masters-<stream>", "id": "'$KAGGLE_USERNAME'/clips-masters-<stream>", "licenses": [{"name": "other"}], "isPrivate": true}' > $WORK/masters-ds/dataset-metadata.json
kaggle datasets create -p $WORK/masters-ds        # private (no --public)
kaggle datasets version -p $WORK/masters-ds -m "add masters of <clip ids>" -r zip      # later uploads add files to the same dataset
```
Then tell the user the dataset name; a master is fetched back with `kaggle datasets download -d $KAGGLE_USERNAME/clips-masters-<stream> -p DIR --unzip`. A rate limit or quota error: retry up to 3 times, then tell the user (never a lower-quality master).

The title (`hook`) is editorial by default: white Playfair text, no box, one italic word (`hook.emphasis`, picked by make_clips), and an automatic dark shade or charcoal text when the picture behind it is bright. `hook.style=pill` gives the old white pill. With `hook.animation=reveal` the editorial title is drawn by the `title-reveal` HyperFrames preset (a little larger, 84 px look).

Layout profile: `layout.profile` is `safe-c` for new clips (game picture y 456-1064, title in the top bar, facecam 300 px wide at x 40-340, y 1250-1475 (a little lower than the first version, still above the bottom zone y 1536), captions y 1100-1500 right of the facecam; everything stays outside the bottom 384 px and the right 162 px of the app) or `classic` (old layout, kept for destinations without app buttons or with no facecam). "Go back to the old layout" = `layout.profile=classic`. "Move the game up a bit more" = `layout.game_shift_extra=70` (clears the top app button from the lower right corner of the picture; offer it once, because the default leaves a 64 px graze). Switching profile with `edit_clip.py` moves the facecam, title, tag, ring, burst and zoom targets with it. In safe-c the ring and burst `xy` are points of the game picture (0,0 is its top left corner), the tag `xy` is a frame point (default `[40,1150]`, above the facecam).

Safe areas: captions never cover the game picture. Before you send a clip with captions on, run `python3 .claude/skills/clips/scripts/check_layout.py CLIP.json --pixels` and expect PASS on every line (with the classic profile, NOTE lines about the platform zones are known limits, not errors). `make_clips.py` writes the same check into the stream's `docs/review.md`. If an edit is refused with a line that names `captions.y_margin` or `captions.position`, use another value or null.

## 7a. Animations (HyperFrames presets; OFF by default, for highlights or when asked)
The title is static by default (`hook.animation=none`). `hook.animation=reveal` animates it (words rise in, a gold line draws, then it leaves; text, italic word and timing come from the `hook` keys, colour and shade from the auto-contrast measurement). `animations.progress_bar=true` draws a 6 px gold line along the bottom edge; `animations.on=true` turns the events on. Events are added only after the user agrees, one edit per clip, then one render:
```
python3 .claude/skills/clips/scripts/edit_clip.py CLIP.json 'animations.events+={"t":4.5,"preset":"callout-ring","text":"HEADSHOT","xy":[556,300],"duration":2}' --render
```
Presets: `callout-ring` (xy = ring end point: safe-c a point of the game picture, x 0-1080 and y 0-608, so the example above is `[556,300]`; classic a point of the 1080x1920 frame; ring moves a little from `from`, label to the left; sits over the game), `lower-third-tag` (xy = top-left of the tag; safe-c default x 40, y 1150 above the facecam, classic x 56, y 1318; leave xy out to use the profile place; clear of the facecam and of the caption box), `impact-burst` (xy = centre, default the centre of the game picture; lines and a shockwave inside the game band, a 0.3 s shake of the game picture only, no flash). Each overlay is rendered once by HyperFrames and cached in `streams/<stream>/docs/cache/` (gitignored); the first render of a clip with overlays takes 1 to 2 minutes, a cached one about 45 s. If HyperFrames cannot run, the animation is skipped, never the clip: the title falls back to the static editorial title, the render prints one WARNING and `ANIMATION SKIPPED` (also the last line of `edit_clip.py`), the exit code stays 0, and you MUST tell a user who asked for animations that they are not available on this machine. A failed event is skipped with one warning line. Check first: `npx --offline hyperframes@0.9.52 --version`. A fresh machine needs Node 22 with npx, npm network for the first run (downloads hyperframes@0.9.52), a Chrome download by HyperFrames on the first render (`~/.cache/hyperframes/chrome`, network too) and about 2 GB of free disk; the first render takes several minutes longer (see CONTROLS.md, Animations). `hook.animation=none` (the default) gives the static title. `check_layout.py` checks the boxes of the title and the events.

## Highlights (when the user asks for 5-6 minute highlights of a stream)
A different video type from the 40-55 s clips: ONE 16:9 1920x1080 YouTube video of snappy, heavily edited highlights. Steps 2-4 (download, transcript, moments) are the same; then, instead of step 5. Highlights need the WHOLE source video as ONE file (`make_highlights.py --video`, `render_highlights.py` has a single source), so: (a) 90 minutes or less with captions: steps 2-4 as written. (b) Over 90 minutes: long mode first (`long_run.py prepare`, `select`, read the candidates), and write the moments you want into `docs/moments.json`; `make_highlights.py` reads that file as its pool. But the whole video cannot be downloaded (step 2 refuses it with `LONG VIDEO`) and the 35 MB window files are not a single source, so a highlights video from a video over 90 minutes is NOT built: tell the user, and offer clips from long mode or highlights from a part under 90 minutes (a file or another link). (c) No captions, 90 minutes or less: the Whisper warning rule of step 3 applies first (tell the user, wait for the go-on, `--accept-whisper`, always `--lang hi` for Hindi); the transcript then exists only for the chosen windows, so word-boundary snapping has no full transcript; this path is untested: tell the user and ask before going on. Then:
```
python3 .claude/skills/clips/scripts/make_highlights.py streams/<stream> --minutes 5-6 --video $WORK/dl/video.mp4 [--moments 12] [--order story|score|time] [--titles FILE]
python3 .claude/skills/clips/scripts/render_highlights.py streams/<stream>/highlights/<slug>      # preview.mp4, post.md; about 10-15 min of CPU
python3 .claude/skills/clips/scripts/edit_highlights.py streams/<stream>/highlights/<slug>/highlights.json OP ... --render   # every control: CONTROLS.md, section Highlights
```
What is asked: the length (default 5-6 min), the order (default `story`: the 2nd best opens, the best closes), whether the girl facecam is wanted (default NO), and read the chapter titles and meme lines before rendering: `make_highlights` gives untitled moments the title "Moment at M:SS", so write real titles (Roman letters, real lines from the moment, `--titles FILE` or `sNN.title=`). On by default for highlights: animations ON (intro title, chapter tags, bursts, progress line; they are OFF for normal clips), automatic crazy editing (zoom punches, hits, risers, ramps, one freeze on the best moment, transitions mixed from slide, zoom-punch, flash, wipe, glitch, fade, cut), sound effects from `assets/sfx` (original, synthesised). Captions OFF, facecam OFF, gameplay always whole. Output: preview 1080p30 (`preview.mp4`, at most 85 MB, local only: NOT committed, see below) or `output.preset=upload` (source fps up to 60, CRF 17, master outside git). Loudness -14 LUFS / -1 dBTP over the whole video.
**Commentary (highlights only, required for YouTube monetisation).** Her English voice-over sits with the stream (reused-content policy, `destinations/youtube-highlights.json`, lesson `youtube-reused-content-needs-commentary`). After the segments are chosen (`H` = the highlights.json, `S` = the stream folder):
```
python3 .claude/skills/clips/scripts/commentary/make_commentary.py $S $H [--en-vtt EN.vtt] [--source VIDEO]   # writes commentary-script.md (the lead fills it)
#   fill the `- at: | text:` lines: 0-2 short English lines (6-18 words; context or a light observation; never invented facts; silence is fine; about one line per 25 s at most; plus an intro and an outro)
python3 .claude/skills/clips/scripts/commentary/make_commentary.py $S $H --ingest
python3 .claude/skills/clips/scripts/commentary/tts.py $H        # Kokoro af_heart on CPU, cached; first time on a machine: tts.py --setup (needs pypi, download.pytorch.org, huggingface.co, github.com once)
python3 .claude/skills/clips/scripts/render_highlights.py <folder>
```
The renderer calls `commentary.mix.build_commentary_track` and ducks the stream with the module's `duck_expr` (0.2 s attack, 0.4 s release, at most 4 dB, only while a line plays); her track (about 7 dB under the stream's loudest speech, `commentary.level_db -7`, `commentary.duck_db -4`) is mixed BEFORE the final two-pass loudnorm. Show the user the script before rendering; `commentary.on=false` skips it. Without commentary (module missing, no lines, or the voice not installed) the render warns `no commentary: not suitable for YouTube monetisation`, still renders, and post.md says so; post.md says "Commentary is present" only when a voice was really mixed in the last render. Tell the user this plainly, plus the Rockstar non-commercial note. Never use any filter to evade copyright detection. Report: `docs/highlights-report.md`.
**Delivering the highlights video:** `preview.mp4` is 80 MB and every re-render would add another 80 MB to git history, so it is NOT committed (`.gitignore`: `streams/*/highlights/*/preview.mp4` and `*_upload.mp4`). Send the video to the user with SendUserFile, path `streams/<stream>/highlights/<slug>/preview.mp4`; only `highlights.json`, `post.md`, `render-report.json`, `commentary-script.md` and `versions/` go to git (step 8). `LATEST.md` and `streams/index.json` list the highlights (path, length, segments, commentary yes/no) and say the video file is local only. The one preview committed earlier stays in history as it is. Never delete a preview to make step 8 pass.

## 8. Publish and record: save at every step, finalise to main once
The container is ephemeral (reclaimed when idle), so nothing waits for "the end". Two kinds of save (lesson `checkpoint-every-step-finalise-squash-to-main`):
- **Work in progress -> the session branch `ccr-*`, automatically.** `make_clips.py` (after EACH clip), `edit_clip.py --render`, `render_highlights.py` and `long_run.py` (after prepare, select, every fetch-windows call, every render batch) call `scripts/checkpoint.py`, which commits only safe files (clip.json, post.md, edit-notes, versions/, poster, preview .mp4 up to 95 MB, docs/*, LATEST.md, streams/index.json; never source/, masters/, windows, `*_upload.mp4`, a highlights preview over 25 MB unless `--big-previews`) and pushes the current branch (5 tries, merge on rejection, never force). It REFUSES a file over 95 MB or one that looks like a key. Output: `checkpoint: pushed <sha> (<n> files, <MB> MB)`. A failure prints `WARNING NOT SAVED TO GITHUB` and never stops a render: run `python3 .claude/skills/clips/scripts/checkpoint.py --stream streams/<stream>` yourself, and say so to the user if it still fails. `.claude/scripts/autosave.sh` also pushes the branch: run `bash .claude/scripts/autosave.sh` by hand at the end of a turn (no hook calls it unless the user added one).
- **Final -> main, in ONE squashed commit, only when the user keeps the clips.** Delete the folders of rejected clips, then:
```
python3 .claude/skills/clips/scripts/finalise.py --stream streams/<stream>          # dry run: checks + plan
python3 .claude/skills/clips/scripts/finalise.py --stream streams/<stream> --yes    # pushes main (fast-forward, never force) and lists the clip files
```
It runs build_index + checkpoint, checks the tree (no file over 95 MB, no key, LATEST.md and streams/index.json list the clips), and commits `clips: <stream>, <n> clips (final)` with the tree of the branch on top of origin/main, so the many re-render blobs stay on the WIP branch only. It refuses if main was changed from another branch (`--accept-main-overwrite` only when the user agrees). The branch is left alone. Rule for main: stream content only through finalise; `autosave.sh` also puts the non-stream files (.claude/, lessons/, README) on main with `finalise.py --sync-docs`.
A master is never committed; a highlights `preview.mp4` stays local (gitignored, sent with SendUserFile, see Highlights) and is NEVER deleted here. `git status --short` should show no masters/ and no source/. Delete `$WORK/dl/video.mp4` once the clips are final. Add lessons and skill changes with `git add lessons .claude` + commit (autosave syncs them to main). The retro (`docs/retro.md`) and the journal (`docs/journal.jsonl`) are in `docs/`: `checkpoint.py` commits them with the stream; the stream's retro is part of the final commit list. Never use `git push origin HEAD:main` for stream files, never force.
**If the container is gone** (new session, nothing local): clone the repo, `git checkout ccr-...` (the branch named in LATEST.md, or the newest `git branch -r --sort=-committerdate`), then `python3 .claude/skills/clips/scripts/jobs.py check`: it lists the running jobs of every stream, whether the process is alive, the Kaggle kernel status and the exact resume command (a COMPLETE kernel is fetched, not run again). Source windows are gitignored (about 35 MB each): fetch them again with `long_run.py fetch-windows` (about 10 min) or, when the user asked for a backup, `backup_sources.py restore --stream streams/<stream>` (optional private Kaggle dataset `clips-sources-<stream>`; `backup` only on request). Clips, clip.json, versions and docs come with the clone; `edit_clip.py` needs the window file again to re-render.
**Long jobs** (every wait on Kaggle, any command over ~2 min) run DETACHED and REGISTERED: `long_run.py prepare|fetch-windows|render` do it by themselves (they print `DETACHED job <id> ...` and follow the log; `--no-follow` returns at once and the job is then NOT finished; `--inline` turns it off). Anything else: `python3 .claude/skills/clips/scripts/jobs.py run --stream streams/<s> --kind NAME --kernel OWNER/KERNEL --expect PATH -- COMMAND...`. The registry is `streams/<s>/docs/jobs.json` (committed; format in the docstring of `jobs.py`), the log `docs/logs/<id>.log` ends with `EXIT <code>`. `jobs.py list|check|resume` read it. `jobs.py tick` is the first action of every turn while a job is open (next paragraph); `jobs.py check` is its read-only twin: if the kernel is COMPLETE and the process is gone, run the printed RESUME line (`--resume-call N` re-attaches to the kernel already on Kaggle: no new push, no new quota; the Whisper two-kernel chain is unproven).
**Tick first, backstop second (every job, lesson `tick-first-during-jobs`).** A local waiter dies with the container or the session; the Kaggle kernel does not. So:
1. The FIRST action of every turn while a job is open (any `streams/*/docs/jobs.json` entry `running`) is `python3 .claude/skills/clips/scripts/jobs.py tick`. It is idempotent, costs no tokens, and prints one `TICK` line: a kernel that is COMPLETE with nothing fetched is fetched by `tick` itself (detached, never a new push); a lost render, a failed job or anything else prints `ALERT` plus the `RESUME` line; with no open job it prints `NO OPEN JOBS` and you stop re-arming.
2. When a job starts, arm the durable backstop: `send_later` at ETA + 10 minutes (ETA from the step's own estimate: prepare about 2 min + 1 min per hour of video, fetch-windows about 10 min, Whisper up to 60 min), message "jobs.py tick first, then continue the clips job for streams/<s>". Each wake runs `jobs.py tick --wake`; if the job is still running, re-arm `send_later` for 15 minutes. At most 12 wakes per job: `tick --wake` counts them and at 12 prints `STOP` with an ALERT: tell the user and stop re-arming.
3. `Monitor` on the job log is only the fast path (it reacts the second `EXIT` appears and dies with the session). `/loop` only when the user is watching live. `create_trigger` (cron) is hourly at best: use it only for a daily sweep of orphan jobs. NEVER depend on ScheduleWakeup or CronCreate surviving a container restart (untested); an archived session is woken by nothing, only the next session's `preflight.py` (it runs `tick`) finds the orphan job.
4. A `UserPromptSubmit` hook could run `tick` automatically; that is a settings change: print the exact line for the user, never apply it yourself.
Every long step also writes `docs/journal.jsonl` by itself (start, end, outcome, retries, seconds lost; `scripts/journal.py`): `long_run.py`, `kaggle.py wait/fetch`, `make_clips.py` and the clip render do it, nothing to remember. What code cannot see goes in with `journal.py note user_correction "TEXT" --stream $ST` (what the user corrected) and `journal.py note agent_error "TEXT" --stream $ST` (what a Haiku or Sonnet agent got wrong); a step done by hand (reading candidates, choosing moments) is bracketed with `journal.py start --step moments --stream $ST` / `journal.py end --step moments --stream $ST`, so an idle gap is not blamed on it.
For each user correction, add a lesson (and the journal note above):
`python3 .claude/skills/lessons/scripts/add_lesson.py --id ... --type ... --stage ... --topic ... --title "..." --rule "..." --why "..." --apply "..." --source 'user: "..."'` (see `.claude/skills/lessons/SKILL.md`).

## 9. RETROSPECTIVE (mandatory, after step 8, lead only, under 10 minutes)
A job is not finished until its retro exists. `long_run.py status` prints `RETRO MISSING` until `docs/retro.md` exists (and `RETRO INCOMPLETE` while a finding has no disposition).
```
python3 .claude/skills/clips/scripts/retro.py --stream $ST                    # builds docs/retro.md from docs/journal.jsonl: time per step, retries, every idle gap, total time lost, findings sorted by time lost
python3 .claude/skills/clips/scripts/retro.py --stream $ST --add "what went wrong that code cannot see"     # your own findings (what the user corrected is already in the journal)
python3 .claude/skills/clips/scripts/retro.py --stream $ST --set F1 "lesson: some-lesson-id"                 # one disposition per finding
python3 .claude/skills/clips/scripts/retro.py --stream $ST --check            # exit 1 until every finding has exactly one valid disposition
```
Each finding gets EXACTLY ONE disposition: `lesson: ID` (added with `add_lesson.py`), `check: WHAT` (a preflight check or a test, built as one small commit with a smoke test), `doc: PATH` (SKILL.md / QUICKSTART.md edit), `backlog: WHAT` (PLAN.md), or `none: REASON` (3+ words). `retro.py` also raises the count of a repeated incident in `lessons/incidents.json` (once per stream; `--incident ID` when you know one happened again). **Rule: an incident with `count >= 2` and `enforced_by: none` becomes a check in `preflight.py` before the next job starts, unless the user defers it** (then the disposition is `none: user deferred ...` and the row gets `"deferred"`); `preflight.py` fails while it is not. Guardrails: never edit settings, permissions, hooks or keys (print the exact change for the user); never force-push or rewrite history; one improvement = one small commit, listed in the retro; other ideas go to the PLAN.md backlog; no improvement work during a user job except a fix that unblocks it. Then commit `docs/retro.md`, `docs/journal.jsonl`, `lessons/` (`git add <paths>` + commit; checkpoint and autosave push them). `audit_due.py` (run by `preflight.py` and `long_run.py status`) counts retros, incidents and lessons for the periodic audit (`docs/audit-prompt.md`).

## Long mode (videos over 90 minutes, up to 5-6 hours)

Steps 2-5 are replaced by `scripts/long_run.py`; steps 0, 1, 6, 7, 8 stay the same. All YouTube access runs in Kaggle kernels. Details and measurements: `docs/long-mode-report.md`.

First create the stream folder: `ST=$(python3 .claude/skills/clips/scripts/download/stream_folder.py "title from the user, or the video id")` (it prints `streams/<YYYY-MM-DD>_<slug>`; `prepare` fills `stream.json` itself).

Every command prints `NEXT:` with the exact next command, and a failure prints one line with the fix.
