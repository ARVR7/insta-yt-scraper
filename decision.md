# Decisions

Every non-obvious decision, with the reason. Newest first. Add an entry whenever you choose between options, work around a limit, or change a rule.

## 2026-10-17

### A failed Instagram fetch is treated as transient, not as a login wall
- **Finding:** issue #3, a public video post, failed with "Fetching Post metadata failed" and I told the user it needed a login. That was wrong: Instagram was intermittently rate-limiting the sandbox (HTTP 429), the tools reported it as vague errors, and the same post downloaded fine when requests were spaced out.
- **Decision:** `fetch_instagram.py` now alternates instaloader and yt-dlp with pauses (10, 20, 40 s) and ends with `RATE_LIMITED:` when the errors look transient. `prepare_link.py` turns that into exit code 4. `process-queue` then uses `retry-1` to `retry-3` labels and retries hourly, and asks the user only after three failed hourly attempts or for a clearly different block (exit 2).
- **Why:** asking the user to paste a caption for a public post is a wrong, annoying answer; one failure is weak evidence. The earlier comment on #3 was corrected.

### Telling Claude's comments from the owner's
- **Decision:** a comment ending in `Generated by [Claude Code](https://claude.ai/code)` is Claude's, even though GitHub shows it under the owner's account. A `needs-input` issue is only retried when its newest comment lacks that footer.
- **Why:** the GitHub tools act as the owner, so "newest comment is by ARVR7" was true for Claude's own request for input, which would have made the scheduled check treat its own text as the missing content. Caught before it ran on a real issue.

### The hourly scheduled task could not reach GitHub, so a standing session replaced it
- **Finding:** the first scheduled task started a fresh session each hour with no GitHub tools and no repository (the task API has no way to attach a repo or connectors, and the creating session had none to pass). Its runs "succeeded" in 25 seconds without reading the queue, so issue #3 sat open for over an hour. A run reports success even when it did nothing, so the run status alone does not show that it works.
- **Decision:** a standing session ("Link Inbox processor") was created with the repository as its source, which gives it the GitHub tools (confirmed: list_issues, issue_write, add_issue_comment). A new hourly task wakes that session instead of starting fresh ones, and the old task is disabled.
- **Trade-offs:** the session keeps its conversation across wakeups, so its context grows slowly (cached, and compacted automatically); empty checks stay one-line replies. If the session is ever archived, the hourly message has nowhere to go and processing stops until it is recreated.
- **Blocked links are not retried on a schedule:** an issue labelled `needs-input` is skipped until the owner comments; the owner's comment is then used as the content (`prepare_link.py --manual`). This stops an inaccessible link being fetched every hour.
- **Issue #3:** Instagram redirected the post to a login page (other public reels still fetched fine), so it is marked `needs-input` and waits for a pasted caption.

### Mechanical front and back halves; the model only judges
- **Decision:** two scripts now carry everything that needs no judgment. `prepare_link.py` does the fetch, frames, transcript (with translation), OCR, candidate extraction and source lookups, and writes a compact `brief.md` plus a draft note. `finish_link.py` takes one small `verdict.json`, writes the note from the draft, files registry entries, rebuilds the library, regenerates the `flow.md` notes table, produces the issue comment and pushes with retries. Claude reads one file, researches, and writes one JSON.
- **Why:** the user asked to make as much mechanical as possible without hurting quality. The model previously retyped boilerplate (metadata, caption, transcript, registry markdown, git commands) and read several large tool outputs; those steps need no judgment.
- **Quality safeguards:** judgment stays with the model (title, category, usefulness, verdicts, which claims to check, research beyond the lookups). `finish_link.py` validates the note and taxonomy before changing any file, rejects leftover `TODO`s, skips duplicate registry entries and never overwrites a note unless asked. The contact sheet is still viewed whenever the video has anything to see; it is skipped only for a talking head with no readable text.
- **OCR is a finder, not a reader:** phone footage of screens gives noisy text (words run together), so OCR is used to surface names, repos and numbers for lookup, and the sheet remains the reference for visual content.
- **Lookups use `raw.githubusercontent.com`:** the sandbox proxy returns 403 for the GitHub API and github.com pages, but raw files work, giving existence, licence and README lines on requirements, limits and price without a model call. A repo not found is reported as unverified, never as fake. Stars and dates need a `GITHUB_TOKEN`.
- **Research budget:** start from the lookups; normally 2-4 searches or page reads per link; none for entertainment.
- **Also fixed:** compiled Python caches had been committed; they are now ignored and removed.
- **Not done:** the hourly scheduled check still starts a model session to list issues. Making that check model-free needs a GitHub Action holding a secret to start the run, which has to be set up by the user.

### Reel DeSArmKIhid (issue #2): FreeVideo, helpful with caveats
- **Decision:** `ai/creative`, usefulness `helpful`, verdict `verified`. The tool is real and open source (checked on its GitHub README and a third-party wiki). The "no other tool does this" claim is filed as `misleading` in `hoax.md`, and the 4K/quality claim as `unverified` in the pending section, so the note is helpful overall but not uncritical.
- **Source hierarchy:** the 8 GB "out of memory" chart is the project's own marketing, so it is treated as a vendor claim and compared against independent guides.
- **Transcription fix:** the `base` model misheard this Hindi audio and printed confident English nonsense. `analyze_video.py` now detects non-English audio and redoes it with the `small` model, writing an English translation plus the original. The first pass is not used.
- **Licence nuance:** the repo (primary source) says code is Apache-2.0 and weights use the MiniMax H3 Community License; the wiki said no licence was stated. The repo wins.

### Theme switch: System, Light or Dark
- **Decision:** a three-way control at the top of Settings. System follows the phone and is the default; Light and Dark override it and are remembered on that phone. The page applies the saved choice before first paint, so there is no flash, and the browser's top bar colour follows the theme.
- **How:** the dark colour tokens are defined once for the OS setting (unless Light is forced) and once for an explicit Dark choice, so each of the three states works whichever way the phone is set. Verified for all combinations in headless Chromium.

### Filters: a sheet behind one button, with removable chips on the page
- **Decision:** a filter button beside the search opens a bottom sheet with Sort (newest, oldest, most useful), Usefulness, Platform, Posted (any time, 7 days, 30 days, this year), Creator and Tool. The button shows how many are active; active ones appear as removable chips under the search; a live "Show N links" button and Reset sit at the bottom. Category, subcategory and location stay on the page as the shelf and chips, and the ring still filters usefulness, so the most used filters need no extra tap.
- **Why:** the user asked for more filtering. Putting the less frequent options in a sheet keeps the page uncluttered, in line with the earlier "too text heavy" feedback. Creator and Tool are dropdowns because they grow without bound.
- **How:** one `matches()` function drives the list and the live count, so they can never disagree. All filters combine (AND).

### Plain, uniform titles
- **Decision:** a note's title names the thing the video is about in 2-6 words (max 50 characters), with no parentheses, hype, verdict, platform or creator. The creator moved to the note sheet's subtitle, and what the thing does plus its main caveat stays in `key_info`. `build_index.py` rejects titles over 50 characters or with parentheses, and the note's first heading must match.
- **Why:** the user found the titles confusing. They were long paraphrases with a qualifier in brackets, which read differently on every card. Short names scan faster and stay consistent as the library grows. Queued links that are not processed yet show `Instagram link · <id start>…` instead of a bare id.
- **Retitled:** "AI YouTube channel automation" and "Higgsfield Katana in Claude".

### Smart categorisation: a closed taxonomy with two axes
- **Decision:** `taxonomy.yml` lists categories, their subcategories, aliases, icons and colours, plus locations (country, then city). Each note has one `category`, a `subcategory` (required when the category has any), an optional `location` and an optional `also` cross-list. The free-form `topics` field is removed.
- **Why:** free tags fragment (`ai-tools`, `video-generation`, `ai-ideas` would have become three AI categories). A closed list, validated at build time, makes that impossible: unknown values fail the build and aliases (`artificial-intelligence`, `Gurugram`) are rewritten to the canonical key.
- **Two axes:** "what is it about" (category) is separate from "where" (location). A Delhi cafe is Food > Eateries in Delhi and a Delhi trip is Places in Delhi, so nothing is filed twice. Places shows its locations as groups, which gives Delhi, Gurgaon, US and UK as asked.
- **One AI category:** all AI content is `ai` with subcategories tools, automation, creative, ideas. Non-AI money and business content is `money`.
- **Locations are only recorded when stated** in the caption, on-screen text or audio. They are never guessed.
- **Cross-listing:** one primary category drives counts; `also` lists a link under a second category without double counting it.
- **Growth:** `scripts/taxonomy.py` merges or renames subcategories, categories and cities across all notes, so a poor early split is one command to fix. New values are added to `taxonomy.yml` under the `categorize-link` rules and logged here.
- **Starting set:** AI, Food, Places, Health & fitness, Money, Tech & dev, Learning & career, Entertainment, Other (capped; use means the taxonomy needs extending). Cities: Delhi and Gurgaon under India; US and UK as countries.
- **Migration:** the two existing reels became `ai/automation` (free AI YouTube studio) and `ai/creative` (Higgsfield Katana).
- **App:** the Library shows a shelf of category tiles with counts; choosing one reveals subcategory chips, then location chips (country, then city). The usefulness ring still filters independently.

### Visual redesign: liquid glass over an aurora gradient
- **Decision:** the app now follows the iOS "liquid glass" direction: frosted translucent panels over a soft aurora gradient, big bold titles, squircle icon tiles whose gradient and glyph encode usefulness (check, wave, cross, dot), a floating pill tab bar, an iOS-style segmented control for Claims, and notes that open as a bottom sheet with a grabber. Dark mode follows the system setting.
- **The ring:** the Library header is an activity-ring style donut split by usefulness; tapping a segment or a count filters the list. It replaces the row of filter chips, so there is less text, not more.
- **Motion:** cards rise in with a short stagger, presses scale, the Working state has a spinner and a sweeping progress bar. Everything respects reduced-motion, and the Queue's one-minute refresh skips the entrance animation.
- **Why:** the plain version read as bland. Colour and shape now carry the meaning (usefulness, state), so the copy can stay short.
- **Type:** Plus Jakarta Sans from Google Fonts with a system fallback, so the app still works offline.

### App simplified: three tabs, short cards, details on demand
- **Decision:** removed the Overview tab, issue numbers, verdict strings, tool tags and explanatory paragraphs. Library cards show title, a coloured usefulness label, platform and a two-line key point. A note opens with title, the key point, "Open original" and topic chips, then collapsible Summary and "What checks out" sections; the full note is one tap deeper. Claims are collapsible cards. Counts appear only as the chips and a badge on Queue.
- **Why:** the user found the first version too text-heavy and complex. Detail is still available, but only after a tap.
- **Topic filter:** the dropdown is gone; tapping a topic chip on a note filters the library, and search also matches topics and tools.

### Hourly scheduled task processes the queue
- **Decision:** scheduled task "Process Link Inbox queue" (hourly, minute :06, fresh session each run, model `claude-sonnet-5-5`). It first lists open `link` issues and stops at once if there are none, so empty runs stay cheap.
- **Why:** the user asked for automatic processing. A fresh session per run avoids a long-lived session and re-reads the repo's `CLAUDE.md` each time.
- **Effort:** the scheduled-task API has no effort setting, so "medium or less" is requested only through the prompt ("keep effort low"). The model was set explicitly, as the user asked.
- **Risks noted:** the task stores no connectors, so a fresh session may lack the GitHub MCP tools; the first scheduled run must be checked. It only acts on issues authored by ARVR7 and on validated Instagram/YouTube URLs.
- **App refresh:** the Queue tab re-polls every minute while visible; other tabs load fresh data on each visit. New app versions arrive on the next load because the service worker is network-first.

### Library: front matter is the source of truth; index and lists are generated
- **Decision:** each note carries `title`, `topics`, `tools`, `usefulness` and `key_info` in its front matter. `scripts/build_index.py` generates `data/library.json` plus `library/` lists by usefulness and by topic. The claim-level files in `registry/` stay hand-curated.
- **Why:** the user expects this to grow a lot. One place to edit (the note) keeps lists consistent, and generated per-topic and per-usefulness files avoid hand-maintained tables that rot. The two granularities answer different questions: `library/` says which videos were helpful, `registry/` says which individual claims are true or false.
- **Usefulness scale:** helpful / mixed / misleading / noise, separate from `verdict` (the fact-check outcome). A video can be a verified tool with deceptive framing (mixed).
- **Validation:** the build fails loudly on missing fields so a note can never silently drop out of the app.

### App reads the repo through the GitHub API with the user's token, not from the public Pages site
- **Decision:** the app fetches `data/library.json`, notes and registries via the contents API (needs Contents: Read-only added to the token). Only the app shell is in `docs/`.
- **Why:** GitHub Pages is public. Notes and the library may be private (the repo may be private), so they are not placed under `docs/`. Cached copies in localStorage give offline reading.
- **Rendering:** a small markdown renderer builds DOM nodes (no `innerHTML`) and only allows http(s) links and in-app note links, because notes contain text scraped from third parties.

### Queue progress uses issue labels
- **Decision:** `process-queue` adds `processing` while working and `needs-input` when blocked; closed means done. The app shows a three-step track and joins finished issues to the library by `platform + id`.
- **Why:** it needs no server and works with the existing token. Progress is only as live as the last time Claude ran, because nothing can push to the app.

### Reel DegLPFbTBpi (issue #1): partly-verified, "free" filed as misleading
- **Decision:** Higgsfield MCP/Katana is `verified-with-caveats`; the "free" claim is `misleading` (subscription and credits required per Higgsfield's own blog); the one-prompt result is `unverified` and listed as pending.
- **Why:** primary sources (Higgsfield blog and MCP page) confirm the product and that it is paid; neither shows prompt-only motion graphics, and the reel shows playback only. The sponsorship is noted as inference, not stated as fact.

### Share-sheet app on GitHub Pages; the queue moves to GitHub issues
- **Decision:** `docs/` is a static installable web app with a Web Share Target. A shared link becomes an issue labelled `link`. `process-queue` reads those issues, comments the verdict and closes them. The artifact queue stays as a second input.
- **Why:** the user wants Instagram/YouTube "Share" to list the app on Android. That needs a manifest `share_target` on a site we serve; the artifact page lives in a sandbox and cannot have one. A static site cannot write to the artifact database, but it can call the GitHub API, so issues became the shared queue.
- **Security:** the token is a fine-grained one the user creates, limited to this repo with Issues read/write only, kept in that phone's `localStorage`, never committed. The repo and label are constants in the page. Issues are untrusted input: only a validated Instagram/YouTube URL is used and issues from other authors are ignored.
- **Duplicates:** the app checks existing `link` issues for the same title before creating one.
- **Service worker:** network-first and same-origin only, so it never touches GitHub API calls and a new deploy is never stale.
- **Tested:** share URL parsing, issue creation and the no-link case against a mocked GitHub API in headless Chromium. Not tested on a real phone or against the real API.

### Link Inbox is a claude.ai artifact with a db queue, not a public website
- **Decision:** a private artifact with the `db` capability holds the queue; `process-queue` reads and updates it through `ArtifactData`.
- **Why:** a public site that triggers scrapers needs a server, and anything that writes to the repo needs a token exposed to the browser. The artifact gives login-protected writes, live status for the user, and no secrets. The GitHub-issue-as-queue alternative was rejected because the page could not show results without a server.
- **Limit:** the page cannot wake Claude, because DB writes do not notify a session. Links are processed when the user asks (a "Copy request" button helps) or when a scheduled task is set up. I did not set up a recurring task without the user's say-so.
- **Seed row:** the first reel was added as `done` so the page opens in a real working state. Its timestamps were approximate, not real clock times.

### Comment analysis added as a lead-finder, not a source
- **Decision:** new `analyze-comments` skill; `fetch_youtube.py --comments N` saves comments; Instagram comments are taken only if the user pastes them or sends a screenshot.
- **Why:** the user said comments may hold useful info but are mostly fake. `instaloader` raises `LoginRequiredException` for comments, and cookies are off the table, so anonymous Instagram comments are impossible. Comments only suggest leads (a repo link, a correction) that still go through `fact-check-claims`; keyword-only replies are treated as funnel noise.
- **Limit:** the YouTube comment path returned 0 comments on the one video tried in the sandbox, so it is untested at volume.

### Verdict categories and where unverified items go
- **Decision:** five verdicts (`verified`, `verified-with-caveats`, `unverified`, `misleading`, `hoax`). Unverified items live in a "Pending verification" section of `registry/verified.md`, not in `hoax.md`.
- **Why:** the user asked for one file of correct items and one of hoaxes. Failing to find something is not proof that it is fake, so it must not be filed as a hoax. The reel's earnings claim is `misleading` (real tools, unsubstantiated promise), which belongs in `hoax.md`.

### Skill split: one skill per reusable operation plus an orchestrator
- **Decision:** `fetch-instagram-post`, `fetch-youtube-video`, `analyze-video`, `write-link-note`, `fact-check-claims`, `update-registries`, and `process-link` that chains them.
- **Why:** the user asked for a skill per distinct operation. Fetching differs per platform, analysis is shared, and fact-checking and filing are independent of the source, so each can be reused alone. `process-link` gives the single entry point for "the user shared a link".

### Scripts live in `scripts/`, skills only describe when and how to call them
- **Decision:** logic is in Python files under `scripts/`; skills hold instructions and known failure modes.
- **Why:** the exact commands were tested once and should not be retyped from memory. Scripts can be fixed in one place.

### Instagram: `instaloader`, anonymous, no cookies
- **Decision:** use `instaloader` for metadata and the video URL, then download it directly.
- **Why:** plain `curl` returns a login shell with no data, and `yt-dlp` was redirected to the login page ("rate-limit for accessing posts anonymously"). `instaloader` returned the author, date, likes, comments and a video URL anonymously. Cookies were not requested because sharing a session cookie is a security risk.
- **Known gap:** it returned `caption = None` for the first reel; the note records "not returned" rather than inventing one.

### Transcription: faster-whisper `base`, audio passed as a numpy array
- **Decision:** decode audio with ffmpeg and hand the array to faster-whisper.
- **Why:** faster-whisper's built-in decoder crashed (`open() got an unexpected keyword argument 'metadata_errors'`) because of a PyAV version mismatch. The `base` model on CPU with int8 is fast enough and accurate enough for short reels; transcripts are labelled auto-generated.

### YouTube: metadata first, media and captions best-effort
- **Decision:** `fetch_youtube.py` saves `meta.json` before trying the download, passes `node` as the JS runtime, and treats captions as non-fatal.
- **Why:** from the cloud sandbox the metadata call works, but the media download returned HTTP 403 and captions HTTP 429. A single combined call lost everything when one part failed. Skills document the fallbacks (use description/chapters, or ask the user for the transcript or file).
- **Not done:** no cookies or proxy tricks to bypass the block.

### Fact-check from primary sources, never run untrusted code
- **Decision:** claims are checked against official docs/policy pages and package indexes; code from the repos in videos is read, not executed.
- **Why:** these videos promote tools from unknown authors; running them is a security risk and not needed to judge a claim.

### Repo: direct pushes to `main`, no PRs
- **Decision:** commit and push every note straight to `main`.
- **Why:** the user said everything should go directly into `main`. The empty repo had no default branch, so `main` was created from the first commit.

### `ARVR7/insta-yt-scraper` created by the user, not by Claude
- **Decision:** the user created the repo and Claude attached it.
- **Why:** the GitHub integration returned 403 on repository creation (not permitted to create repos), so the user made an empty repo.

### Reel DeToMLxtdSV: verdict "partly-verified"
- **Decision:** tool components `verified-with-caveats`, the specific repo `unverified`, the income claim `misleading`.
- **Why:** see `notes/instagram/DeToMLxtdSV.md`. The repo name could not be found in two searches and the owner is not legible on screen.
